# Compiler Frontend Migration Follow-up

This is the implementation checklist for [`COMPILER-FRONTEND-ARCHITECTURE.md`](COMPILER-FRONTEND-ARCHITECTURE.md). Statuses describe repository work, not promises. A phase advances only when its acceptance checks pass; the legacy compiler remains the default until Phase 7 promotion.

## Audit and finite acceptance model

The prior checklist mixed code tasks with local, CI, specification, and release-lifecycle acceptance, which made the remaining work appear to move as individual edge cases were found. This section is the gate for interpreting the checklist below. It does not reduce the migration scope; it makes completion evidence finite and assigns each kind of evidence to its proper stage.

| Evidence class | Required finite evidence                                                                                                                                                                                                                                                                                                                                                                                                               | Does not imply                                                                                                                                    |
|----------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------|
| `LOCAL`        | Every normative example in the versioned language/compiler specs parses and has an expected materialization; each documented construct has a valid fixture, and each diagnostic-producing construct has representative invalid-boundary fixtures.                                                                                                                                                                                      | Exhaustive testing of all token combinations or all C programs.                                                                                   |
| `INTERACTION`  | A maintained fixture matrix exercises the semantic boundaries that cross pass ownership: nested/generated comptime declarations and fixed-point expansion; conditional selection before imports/flags; imports plus source maps; scalar materialization before test extraction; methods/receivers with try/defer; generated declarations followed by runtime lowering. Add a case when a concrete pass-order dependency is introduced. | The Cartesian product of every feature, target, and syntax spelling.                                                                              |
| `DIFFERENTIAL` | Maintain a finite, migration-only overlap corpus: for syntax both frontends accept, compare normalized results, options, mapped diagnostics, and executable behavior where applicable. Keep comparisons for high-risk migrated behavior until the AST path is authoritative for that slice.                                                                                                                                            | Making legacy parser limitations normative, requiring differential coverage for AST-only syntax, or maintaining a duplicate whole-language suite. |
| `CI`           | Run grammar/JVM/compiler tests and native parser load/package smoke tests on each supported host OS/architecture. Record workflow evidence; local Linux results cannot close this gate.                                                                                                                                                                                                                                                | Waiting for CI as a substitute for a missing local regression.                                                                                    |
| `RELEASE-SOAK` | Only after promotion: keep legacy selectable for two stable releases, track mismatch reports, publish rollback instructions, then decide legacy retirement separately (Phase 9).                                                                                                                                                                                                                                                       | A prerequisite for implementing Phases 1–8 or a reason to delete legacy during this migration.                                                    |

Specification changes are not an automatic response to a failing test. First classify the failure as (a) implementation defect against an existing normative rule, (b) genuinely ambiguous/conflicting spec text, or (c) an explicitly unsupported prototype slice. Only (b) warrants changing normative language; (c) must be reported as unsupported, not silently excluded from the final conformance inventory. Keep prototype capability notes in sync, but do not repeatedly expand the language contract to fit implementation behavior. For AST-only syntax, use normative expected-output, diagnostic, source-map, and C compile/run tests; do not force the legacy frontend to accept it merely to create a differential test. The overlap corpus is retired slice-by-slice after AST promotion, while the full specification-driven tests remain.

Phase work is reported against its gate ID and evidence class. Do not start unrelated IDE polish while a compiler gate is active; Phase 8 editor migration has its own bounded acceptance checks. The legacy compiler remains production-authoritative throughout Phases 1–8.

## Finite implementation case ledger

The phase descriptions are gates; this ledger is the measurable work breakdown behind them. A **case** is one independently observable language/compiler invariant with a fixture, an expected result or diagnostic, and a repeatable acceptance command. It is not every possible Cartesian combination of syntax, types, targets, and pass order. A newly discovered defect is added under an existing case unless it introduces a new invariant or evidence class. This prevents the target from moving every time a spelling variant is found.

Status meanings:

- `DONE`: the bounded case has passing repository evidence.
- `MIGRATED-FALLBACK`: the AST replacement has bounded parity, source-map, and rollback evidence; the legacy implementation is intentionally retained as the production default or explicit fallback.
- `IN PROGRESS`: implementation or acceptance evidence is incomplete.
- `OPEN`: planned work remains locally.
- `OPEN-EXTERNAL`: local configuration is present, but only CI or another host can close it.

Effort is deliberately coarse and relative: `S`, `M`, `L`, and `XL` carry 1, 2, 4, and 8 planning points. They are not promises of calendar time; related cases can share implementation and CI work. Track velocity as weighted points per week, not by raw checklist count. Convert points to hours only after recording actual time for several completed rows.
