# C-plus Compiler Frontend: Target Architecture

Status: architecture plan, not a normative language specification. Existing behavior remains authoritative until a phase is implemented and its acceptance gate passes. Track implementation in [`COMPILER-FRONTEND-IMPLEMENTATION.md`](COMPILER-FRONTEND-IMPLEMENTATION.md).

## Goals and boundaries

The compiler should parse C-plus structurally, retain exact source provenance through every transformation, and continue emitting portable C for the existing TinyCC/system-compiler backends. Parser choice must not leak into language lowering. The old text-based frontend remains usable during migration; no feature is removed merely because a new parser can recognize it.

“Flawless” is not a realistic guarantee. The target is predictable behavior backed by grammar conformance tests, mapped diagnostics, differential migration checks, fuzzing, and measured performance. Tree-sitter is a parser/CST engine, not the semantic AST, type checker, preprocessor, or C backend.

## Target pipeline

```text
project/import graph
  -> immutable source snapshots and coordinate maps
  -> selectable parser backend
  -> lossless C-plus CST with recoverable syntax diagnostics
  -> normalized C-plus AST and symbol/type model
  -> comptime/import expansion to a fixed point
  -> semantic validation and runtime lowering IR
  -> C AST / structured C emission with source map
  -> existing external C compiler (TCC, CC, or configured compiler)
```

Each stage consumes an explicit value and returns an explicit value plus diagnostics. Stages do not discover structure by rewriting arbitrary substrings. Generated syntax is parsed again at the phase boundary where it becomes active. The C compiler remains the authority for C ABI details and final C validity.

## Component specifications and solution sketches

### 1. Source manager and source snapshots

Own canonical source identities, immutable file contents, revisions, import relationships, and encoding/coordinate conversion. A snapshot exposes C-plus UTF-16 offsets used by current Kotlin code, UTF-8 byte offsets used by Tree-sitter, and line/column spans. A parser node span must always map back to a source snapshot; generated text carries origin segments rather than fabricated file positions. Cache a snapshot for unchanged content and increment its revision when content changes. Imports are resolved by a separate policy using project roots, standard-library roots, and relative paths.

Initial implementation adds `SourceId`, `SourceSnapshot`, `SourceCoordinateMap`, and `SourceManager`, reuses the existing `SourceFile` span model, and routes the root input through the manager. It deliberately does not yet replace comptime import loading.

### 2. Frontend backend contract and selection

Expose a narrow compiler API: parse a `SourceSnapshot` under an explicit dialect/target/options value and return a backend-neutral parse result, diagnostics, and backend identity. Backend implementations own lexing where their parser combines lexing and parsing. Selection is explicit (`legacy` or `tree-sitter`) through an internal compiler option, with the current backend as the default until promotion. Do not expose Tree-sitter `Node` or numeric symbol IDs to compiler passes. Keep CLI/parser selection experimental until output behavior is stable.

Migration implementation: `CPlusParserShadowRunner` parses with an authoritative backend and an observational backend in one call. It records coverage, diagnostics, and normalized-node fingerprint differences, plus syntax-span parity for the comptime/test subset both implementations recognize, while preserving both results. Trailing whitespace accidentally included in legacy scanner spans is trimmed only for the comparison key. Its `errorLocationsAlign` metric checks that errors from each backend intersect an error range or zero-width insertion point from the other backend; this is a coarse location gate, not exact diagnostic parity. A malformed `@type` fixture exposed an offset-zero legacy missing-body diagnostic, now anchored at the expected closing-brace position. Ordinary C/C-plus remains opaque in the legacy adapter, so whole-tree differences are expected and no output or diagnostic policy switches based on this prototype. The CLI exposes `parse --backend legacy|tree-sitter` for explicit parser inspection while retaining Tree-sitter as its existing default; compilation remains on the legacy production compiler. Shared-construct parity covers all current C-plus files under `stdlib/` and `examples/`; malformed shared comptime function, flags, import, block, test, and legacy type-generator forms are checked for rejection and source-contained, mutually aligned error locations. Exact diagnostic ranges/messages and emitted-output parity remain open.

### 3. Tree-sitter C-plus grammar module

Keep the upstream C grammar, license, provenance, pinned revision, generator version, and local changes together in a dedicated module. Extend its grammar to recognize valid C-plus constructs directly: struct-contained methods, annotations, receiver calls, comptime declarations/blocks/invocations, `defer`, checked error calls, and test fixtures. Define named nodes and fields for constructs consumed by later passes. Use external scanners only for lexical state that cannot be expressed cleanly in the grammar. Recovery `ERROR`/missing nodes are diagnostic input and a migration aid, never the normative C-plus syntax boundary.

Check generated parser artifacts into the repository (or make generation reproducible in CI from the pinned toolchain); regular compiler builds must not need a parser generator download. The reproducibility gate byte-compares generated `grammar.json`, `node-types.json`, and `parser.c` with their checked-in counterparts. Preserve upstream attribution/license and record the fork point. Build and package the Tree-sitter runtime and language parser for supported hosts, or select a compatible Kotlin/JVM binding after validating Java 21, native loading, and distribution size. The six-host CI matrix stages the grammar JNI libraries into the CLI JAR; release packaging checks their resource paths. This packaging decision is a phase gate, not an assumption, and host runtime checks still gate promotion.

### 4. CST-to-AST adapter

Translate grammar-specific concrete nodes into stable C-plus AST types with source spans and references to retained syntax/trivia where source-preserving output is useful. Normalize aliases and equivalent syntax once. The initial compiler-facing categories distinguish structs, unions, enums, enum lists and enumerators, typedefs, declaration/field lists, fields, variables, functions, methods, types, declarators, initializers, annotations, generic type parameters, attributes, designators, parameter/argument-list containers, comments, identifiers (including goto labels), control flow, preprocessor directives, and C-plus constructs. Common variadic parameters, bit fields, concatenated strings, assembly-expression parts, and ABI/preprocessor helpers map into these stable families while retaining their grammar kinds. Declaration classification follows C declarator binding order: a function-pointer object is a variable even though its type contains a function layer, while function prototypes and functions returning pointers remain functions. Original grammar names and source spans remain available on every adapted node. Unknown/recovered nodes remain representable and diagnostic-bearing; they must not be silently dropped. A dedicated AST schema and exhaustive adapter tests prevent generated grammar changes from cascading into every pass.

### 5. Module graph, preprocessing, and comptime

Represent source imports as a graph with canonical identities, cycle diagnostics, and deterministic dependency order. Keep ordinary C `#include` semantics delegated to the C compiler. Parse C-plus `comptime import`, resolve comptime definitions, evaluate permitted values, and materialize generated C-plus declarations until no active comptime forms remain. Generated declarations are parsed on the next expansion iteration, with origin segments chained to the generator call/body. The evaluator stays sandboxed and bounded as specified in `SPEC.comptime.md`; it consumes AST nodes rather than rescanning source text.

Current transition: the established evaluator remains the production authority and the compilation result exposes canonical import edges and dependency-first `sourceOrder` metadata via `TranscodedSource`. The Tree-sitter prototype now resolves module-scope modern `comptime import` and legacy C-plus `@import` nodes through the shared path resolver, leaves nested generator-body imports dormant, diagnoses imports in runtime scopes, deduplicates modules, rejects cycles, materializes supported OS conditions before import discovery, emits dependencies before importers, and preserves each module's source origins. It also lowers parsed C `@import("...c")` nodes to ordinary absolute `#include` directives. Tests cover nested relative/`stdlib:/` imports, duplicate edges, cycle spans, imported scalar comptime values, imported test/assertion origins, and generated C execution. The experimental parser indexes legacy `@fn` generators, `typedef @generator(T) Alias;` specializations, and nested `comptime code` declarations; each nested construct records its nearest enclosing generator span and remains dormant until materialization. Generator signatures/result kinds, parameters, invocation spans, and aliases are retained in the AST index. The prototype materializes structural OS conditions (`os == "..."`, `os != "..."`), a bounded module-scope integer/bool scalar subset, and AST-indexed `comptime flags`; generated literals retain source origins and compiler options preserve first-seen order. Unsupported condition/value forms and out-of-scope flags fail closed. Comptime generators, strings/reflection, architecture predicates, and general compile-time evaluation remain legacy-only; the prototype does not change production resource limits. `cplus graph file.cp` serializes import metadata as `cplus.imports.v1`; VS Code, IntelliJ, and Vim import-graph actions consume the graph and navigate to selected imports. Runtime emission remains dependency-first as before; the JSON projection does not change generated C.

### 6. Name resolution and semantic model

Build scopes and symbol tables for C declarations, typedef names, structs, fields, methods, static methods, comptime names, and annotations. Runtime semantic indexing must exclude dormant declarations inside comptime generators/blocks/conditionals and become aware of generated declarations only after materialization and reparsing. Resolve `receiver.method(...)` against declared receiver types and pointer/value forms while preserving pointer depth through typedef aliases, parameters, and fields; a pointer-to-pointer is not treated as a direct instance, while explicit dereference can recover the pointee receiver. Inside an instance method, infer an untyped `self` receiver from its enclosing struct. Explicit parenthesized `&value` and `*pointer` receiver expressions are normalized for type lookup; chained field receivers are resolved through declared field types, and already-pointer receivers are passed without adding another address operator. Preserve an explicit distinction between `@throws()` (error-return) and `@throws(name)` (error-out), with the annotated declaration's parameter symbols available for validation and call rewriting. Resolve `@throws` declarations to call sites, validate catch codes/parameters, and retain ownership/access annotations as metadata without enforcing them unless the language specification later changes. C preprocessor expansion is not reimplemented here; unresolved macro-dependent C constructs remain delegated to the C compiler or receive explicitly documented limits.

The opt-in semantic prototype reports known receiver-kind errors: static methods used through values and instance methods used through type names. It also recognizes the established explicit-receiver form `Type.instance_method(&value, ...)` when the first argument resolves to a single pointer of the qualified type; this is distinct from a static call and lowering must not synthesize a second receiver. File-scope value declarations seed receiver lookup (including simple declarations nested in preprocessor branches), while typedef names do not enter value scope; comma-separated object declarators are indexed individually. Ordered pointer/array/function declarator layers preserve distinctions such as an array of pointers versus a pointer to an array through aliases, variables, parameters, and fields. Subscript expressions consume one outer array/pointer layer, supporting value arrays, arrays of pointers, pointer-to-array and multidimensional forms. Receiver validation considers the complete remaining declarator shape: `.` requires a value receiver, while `->` accepts a direct pointer or a C array-of-struct expression that decays to that pointer; arrays of pointers and pointers to arrays must be indexed or dereferenced first. The explicit C-plus `(&value).method()` form remains supported, while pointer-to-pointer receivers require explicit dereference. Receiver-kind/operator/depth/declarator-shape diagnostics retain the call span and cause the experimental transpiler to fail closed. `for` initializer declarations have a dedicated scope visible to the condition, update, and body but not to following statements. This supports singleton-style C-plus wrappers such as xmem and ordinary C declarations such as `widget_t value, *pointer;`. Unknown external members and macro-dependent receiver types remain unresolved rather than being guessed.

Initial semantic support also records function-pointer typedefs as callable signatures, preserving the base result type, parameter names/base types and original parameter declaration spellings, variadic marker, and declarator span. The typedef symbol retains its exact original declaration text so pointer/qualifier placement is not lost while deeper declarator normalization is incomplete. Callback signatures nested in function-pointer parameters and returned-function-pointer composition are indexed recursively; a C11 fixture exercises these declarations and attributes by compiling/running with each locally available `cc`, `gcc`, and `clang` driver. Active comptime invocations now bind to indexed generator declarations by symbol and arity, producing mapped unresolved/arity/ambiguity/duplicate diagnostics while ignoring nested dormant generator syntax. Generator definitions inside runtime functions/struct bodies are excluded from the module comptime namespace, while runtime invocations can bind to module-level declarations. This is declaration binding only: the legacy evaluator remains authoritative for argument typing/evaluation and materialization. The opt-in allocation analyzer validates known provenance for annotated global/method parameters and function/method returns, plus owned double-pointer outputs, and carries explicit annotated call-return domains into surrounding arguments. Its branch joins compare allocation domains rather than allocation-site text; sequenced comma writes update flow, while `&&`/`||` and conditional-expression joins discard provenance when a path may skip or disagree. Function-call arguments are analyzed on independent snapshots, and potentially conflicting writes invalidate stale prior provenance. Calls passing `&variable` to annotated owned double-pointer parameters conservatively invalidate caller provenance unless the incoming and declared output domains agree. A loop diagnostic walk invalidates known provenance for assigned outer variables after `while`/`for`/`do`, without claiming fixed-point convergence; `for` initializer declarations remain local. General unsequenced binary operand combinations and loop fixed-point analysis remain unmodeled. Explicit type-qualified instance calls align the explicit receiver separately from user arguments for allocation-contract checks. It does not yet validate function-pointer assignments or all qualified/deep declarator compatibility; cross-host compiler verification remains a gate.

Switch cases are now diagnostic-walked independently from conservative snapshots in a local scope; provenance for any outer pointer assigned in the switch, including one potentially written through an annotated owned double-pointer call such as `replace(&value)`, is invalidated afterward because cases may be skipped or fall through. This prevents one case's assignment from becoming a false assumption in a sibling case, but remains one-pass analysis rather than a case-sensitive switch data-flow solution.

### 7. Lowering IR and ordered transformations

Use typed, source-spanned runtime IR (or a normalized AST with explicit lowered nodes) for C-plus-only behavior. Lower in named, testable passes: implicit receiver insertion/method names; `defer`; `try`/`catch`; test harness extraction; and optional allocation diagnostics. Each pass declares prerequisites and invariants, returns diagnostics, and preserves source origins. The prototype now uses `CPlusAstLoweringPipeline` to execute ordered transformations, enforce AST/source snapshot agreement, reparse changed results before the next pass, record pass traces, and stop immediately on lowering or parser errors. This is a safe orchestration layer over AST transformations, not yet the dedicated typed lowered-node IR described here. The transition prototype extracts/validates `@throws` metadata and AST-lowers standalone checked calls plus error-out assignment/initializer values through nested ordered catches. It also has an opt-in AST allocation-intent analyzer for annotated-variable mismatches, direct allocator calls, simple initializer aliases, standalone direct identifier assignments, annotated global-function parameter and return checks (combining prototype/definition contracts), owned double-pointer output writes, resolved instance/static method parameter checks, and annotated method return checks using known allocator/parameter provenance. Explicit call-return domains propagate to surrounding argument checks. An `if/else` join retains provenance only when both paths agree (a missing `else` is the unchanged incoming path), and a conditional expression has known provenance only when both value arms agree; divergent branches, loops, and short-circuit assignments remain unknown. Larger checked-call expressions fail with mapped diagnostics. Comptime syntax is absent before runtime lowering. Avoid serial string replacements for semantics or control flow.

### 8. C representation, emitter, maps, and diagnostics

Emit C from structured nodes with a mapped writer. The output map records generated byte/line ranges to original snapshots and spans, including generated text with multiple contributing origins. Origin lookups use half-open character offsets; the legal EOF boundary has no character origin and must return `null` rather than indexing past the buffer. Continue emitting `#line` for compiler compatibility, but use the explicit map to normalize compiler diagnostics precisely. Keep diagnostic severity, code, related spans, and notes independent of terminal formatting. Preserve the public `TranscodedSource`/CLI behavior as a compatibility facade while its internals migrate.

Current transition: fixture and `@throws` removal, `defer` placement, struct-method extraction, receiver-call lowering, and checked-call/try-catch lowering in the experimental pipeline use node-keyed replacements and before/after-node insertions through mapped AST traversal. Nested receiver calls are rendered recursively within their owning call-expression node; nested try nodes and checked-call statements are replaced inside mapped AST subregions, preserving untouched trivia and origin segments. The prototype's final C stage traverses normalized AST terminals, emits exact token spellings with deterministic brace/statement layout, parenthesis-aware semicolon handling, AST-context punctuation, and indentation, preserves token origins, and leaves preprocessor regions verbatim. It reparses the final output before exposing it and rejects recovered, opaque, or unlowered C-plus nodes. Full grammar-aware formatting and semantic generation for all C nodes remain open; allocation analysis remains separate and production transpilation remains on the legacy emitter.

The final emitter must treat a C literal as a single spelling unit: Tree-sitter exposes string quotes, content, escapes, and character literal components as children, but adding layout between those children changes runtime values. Initial executable differential fixtures compile the same method/receiver, `defer`, and checked-call programs through both paths and compare exact stdout and exit status; the method fixture also checks generated source-map locations. They cover a format string, adjacent string literals, an escaped character literal, reverse-order deferred work, and caught error propagation across consecutive `@try` statements. The grammar treats `@try` and `@catch` as atomic keywords so comptime interpolation cannot recover across adjacent handlers. Broader syntax, diagnostics, and target coverage still gate promotion.

### 9. IDE and tooling consumers

Use the parser contract and shared node names for indexing, outline, navigation, completion, test discovery, and diagnostics. `cplus parse file.cp [-o ast.json]` exposes the versioned normalized result for saved files, while `cplus parse --stdin --source file.cp` parses an unsaved editor snapshot; `cplus graph file.cp` exposes resolved imports as `cplus.imports.v1`. VS Code and IntelliJ **Show Import Graph** actions consume the graph, while Vim's `:CPlusImportGraph` presents imported files in its location list; VS Code also projects a current normalized parse tree into outline symbols and Test Explorer fixtures when parser diagnostics are enabled, with its lightweight index/scanner as fallback. Vim exposes a normalized-AST location-list outline through `:CPlusSymbols`; both parse and symbols commands pass live buffer contents through stdin. IntelliJ caches the external annotator's normalized AST for exact source snapshots and uses it for struct member completion, Go to Declaration, the native Structure view, and test-gutter fixture names/spans, with text-index fallbacks where supported. Import-graph resolution remains disk-backed; broader editor feature parity remains open. Keep editor-specific presentation adapters separate. VS Code can update trees incrementally; IntelliJ can consume snapshots/results through its platform APIs; Vim can use CLI JSON diagnostics or a future language server. Editor features must degrade gracefully on recovered/incomplete syntax.

### 10. Verification and performance

Maintain a corpus covering valid C, every documented C-plus construct, C preprocessor directives, imports, Unicode, malformed/incomplete editor buffers, and generated source. Compare legacy and new backends on accepted source, symbols, emitted C, diagnostics, and source maps. Add grammar corpus tests, transformation golden tests, property/fuzz tests, cross-platform native-loading tests, and cold/warm parse benchmarks. The opt-in benchmark measures fresh-parser repository batches, generated parse/transcode workloads, selected real stdlib/example transcodes, fresh full reparse, and an incremental session that edits/reparses with the prior Tree-sitter tree. That session currently rebuilds the normalized compiler AST from the resulting CST, so its timing is not yet editor end-to-end performance. Performance budgets are measured before parser promotion; incremental speed alone does not justify slower or less correct batch compilation.

## Migration and component lifetime

| Component | Introduced / transition | Lifetime and replacement condition |
|---|---|---|
| Existing `SourceFile` and `MappedText` | Retained in phase 0; wrapped by source snapshots | `SourceFile` becomes a compatibility view in phase 7. `MappedText` expires only after every text-only pass is retired and all origin-map tests pass; replaced by source-spanned nodes plus mapped emitter segments. |
| Existing comptime scanners/evaluator | Legacy backend during phases 0–4 | Retire scanner parsing only when the Tree-sitter AST handles all normative comptime forms, fixed-point expansion and import tests pass, and output/diagnostics match the legacy corpus. The evaluator's sandbox and semantics remain; its input representation changes. |
| Existing textual `DeferLowerer` | Legacy lowering in phases 0–5 | Replace during phase 6 with `DeferLoweringPass` over function/block nodes. Delete only after early-return, nesting, ordering, comments, and source-map regression suites pass. |
| Existing method/type lowerers | Legacy lowering in phases 0–5 | Replace during phase 6 with resolved method-call and struct-method AST passes. Delete after receiver inference, static/instance distinctions, and emitted-C compile tests match. |
| Existing error annotation/try-catch lowerers | Legacy lowering in phases 0–5 | Replace during phase 6 with resolved-call/control-flow lowering. Delete after nested handlers, explicit error arguments, exact-once evaluation, and mapped diagnostics pass. |
| Existing allocation analyzer | Used through phase 5 | Reimplement as semantic-model traversal in phase 6; remove old scanner once annotation/provenance diagnostics are equivalent. Ownership stays advisory. |
| Existing `MappedEmitter` | Used as compatibility output throughout migration | Its API survives; its text input implementation is replaced in phase 7 by structured emission. Keep `#line` until external compiler diagnostics are verified against explicit maps on all supported platforms. |
| Legacy frontend selector/backend | Default in phases 0–6; differential mode in phase 7 | Deprecated when the new backend passes all promotion gates. Remove no sooner than two stable releases with the new backend default, a documented rollback path, and no unresolved corpus differences. |
| Tree-sitter runtime/parser | Prototype in phase 2; opt-in through phase 6 | Long-lived parser backend, replaceable behind the frontend contract. Upgrade only with pinned generator/runtime compatibility and full corpus/benchmark validation. |
| CLI/IDE compatibility facades | Kept during all phases | Long-lived public surface; delegate to the selected frontend. Change only through documented compatibility policy. |

## First transition step

Implement the source manager and coordinate map, without switching parsing or altering generated C. It gives both frontends one source identity/revision model and establishes the UTF-8 byte ↔ Kotlin UTF-16 mapping needed by Tree-sitter and editors. Gate completion on ASCII and multibyte round trips, rejection of offsets inside encoded code points, stable unchanged snapshots, revision changes on edits, and the full existing CLI test suite. Then add the backend contract and a legacy adapter as the next separately reviewable step.
